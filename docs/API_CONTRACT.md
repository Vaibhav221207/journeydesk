# C++ API contract

All responses are JSON except static HTML/CSS/JS/SVG. Errors use `{ "error": "message", "fields": { "field": "message" } }` and HTTP 400 validation, 401 missing/wrong desk key, 404 not found/wrong ticket contact, 409 occupied/duplicate/cancelled, 413 oversized body, 415 content type, 503 storage. Transport dates are strict `YYYY-MM-DD`. Normal booking dates range from today to 365 days ahead. Demo uses a separate journey namespace; GETs never seed data.

## C++ interface (namespace `journey`)

`using json = nlohmann::json;`

`class AppError : public std::runtime_error { public: int status; json fields; AppError(std::string message, int status = 400, json fields = json::object()); };`

`class ReservationEngine { public: explicit ReservationEngine(std::filesystem::path storage_path, std::string today_override = ""); json catalog() const; json search(const json& input) const; json journey(const json& input) const; json book(const json& input); json book_group(const json& input); json ticket(const json& input) const; json cancel(const json& input); json manifest(const json& input) const; json load_demo(const json& input); };`

Thread-safe engine. `storage_path` empty means in-memory. Root owns `include/web.hpp`, `src/web.cpp`, `src/main.cpp`, transport tests and build/deployment. Engine implementer owns `include/engine.hpp`, `include/structures.hpp`, `src/engine.cpp` and `tests/engine_tests.cpp`. UI implementer owns `static/` only. Root supplies bundled `vendor/json.hpp`, `vendor/httplib.h` and licences. No arbitrary Python code or old Python files in new submission.

## Service and ticket shapes

Service: `{id,number,name,mode,source,destination,departure,arrival,arrival_day_offset,duration_minutes,fare,capacity}`; mode exactly `Bus` or `Train`; fare integer rupees; source/destination city names; hours `HH:MM`; capacity 12 bus / 18 train.

Ticket: `{reference,passenger_id,name,age,gender,contact,service,date,demo,status,seat_number,queue_position,fare}`. Status exactly `Confirmed`, `Waiting`, `Cancelled`. Service is the complete service object. Seat and queue position are integer or null. Cancelled history remains searchable. Normal passenger IDs are generated by backend (`P000001` style); reference is an unguessable `JD-` token. Gender exactly `Female`, `Male`, `Other`, `Prefer not to say`; age integer 1–120; name trimmed 1–100 chars; contact normalizes +, spaces, parentheses, hyphens to 10–15 digits. No HTML interpolation in UI.

Public journey: `{service,date,demo,seats:[{number,status}],counts:{available,booked,waiting}}`; seat status `Available` or `Booked`, no personal records or names.

## Routes

- GET `/api/catalog` → `catalog()` returns `{cities:[...],services:[...],today,default_date,max_date,demo_service:"GJ01",demo_date,max_passengers_per_booking:6,backend:"C++20"}`. Default date tomorrow, Kolkata timezone +05:30.
- GET `/api/search?source=Ahmedabad&destination=Mumbai&date=...&mode=Bus` → `search(input)` returns `{source,destination,date,mode,results:[{service,available,booked,waiting}]}`. Same/unknown cities invalid; valid route with no match returns empty array. Sort by departure.
- GET `/api/journey?service_id=GJ01&date=...&demo=false` → `journey(input)` returns public journey. Missing demo defaults false. Transport query parser converts `true`/`false` to actual bool and rejects other values.
- POST `/api/book` → `book(input)` where input `{service_id,date,demo:false,passenger:{name,age,gender,contact},seat_number:null}`. Returns `{message,ticket,journey}`. Omit preferred seat or null for automatic. When full, join FIFO. Preferred occupied seat returns 409, not silent reallocation. Duplicate active contact+name on same journey returns 409, while different people on same contact are allowed. Future normal journeys only. Read and cancel previously booked journeys remain allowed after date passes.
- POST `/api/book/group` → `book_group(input)` where input `{service_id,date,demo:false,contact,passengers:[{name,age,gender,seat_number:null}]}`. One to six travellers share the top-level contact. Members contain only `name`, `age`, `gender` and optional `seat_number`; member contact/internal overrides are rejected. Returns `{message,tickets:[Ticket...],journey,total_fare,counts:{confirmed,waiting}}`, with tickets in submitted passenger order. Each ticket has its own ID and reference and remains independently searchable/cancellable with the shared contact. Total fare is the sum of the sample fare for every submitted passenger; no payment is collected.
- POST `/api/ticket` → `ticket(input)` where input `{reference,contact}`. Returns `{ticket}`; wrong contact and missing reference produce same 404. Lookup searches normal and demo history.
- POST `/api/cancel` → `cancel(input)` where input `{reference,contact}`. Returns `{message,cancelled,promoted,journey}`; cancelled is ticket. `promoted` null or `{passenger_id,name,seat_number}` in demo, and `{seat_number}` for normal (no disclosure of next traveller). Contact auth always required. Repeated cancellation 409. All later queue positions update.
- GET `/api/desk?service_id=...&date=...&demo=false&q=...` → `manifest(input)` returns `{journey,passengers:[ticket...],waiting:[ticket...]}`. Includes only active records, confirmed sorted by seat and waiting by actual queue order. Optional q case-insensitive passenger ID/name/reference filter; queue positions remain original unfiltered values. Server requires `X-Desk-Key` header for normal manifests; fictional demo doesn't require a key.
- POST `/api/desk/cancel` → server authorizes same as desk then calls engine `cancel(input)`. Body `{reference,service_id,date,demo}`. Engine allows contact omission ONLY when internal input `_desk_authorized:true` added by server after checking access; never trust that field from public request.
- POST `/api/demo` → `load_demo(input)` where `{reset:false}`. Returns `{service_id:"GJ01",date,demo:true,journey}`. First call loads 12 confirmed, P108 Neha Patel / P109 Raj Kumar / P110 Amit Patel waiting. P102 Priya Patel holds seat 2, P101 Rahul Shah seat 1, P103 Amit Shah seat 4. Calls preserve current demo unless reset true. Reset touches demonstration namespace only. API documentation explicitly says fictional sample data. Demo mutations restricted to GJ01 and demo_date; do not create arbitrary demo journeys.
- GET `/api/health` transport returns `{ok:true,backend:"C++20"}` without storage paths or keys.

Static routes `/`, `/static/index.html`, `/static/styles.css`, `/static/app.js` and `/static/scene.svg` only. Do not expose source, JSON data, executable, access keys or include headers. No wildcard static directory mounting. Same-origin POSTs, bounded body sizes, CSP, no cache for API. Mutating normal book requests cannot include internal flags. One engine process owns storage.

## Group allocation and atomicity

Validate the complete group before committing any change. Invalid members, duplicate active normalized name/contact pairs, duplicate preferred seats within the group, already occupied preferred seats, and storage errors reject the entire request. No partial tickets, consumed passenger IDs or altered seats may remain after failure. Error fields identify `contact`, `passengers`, or an indexed field such as `passengers.1.name` or `passengers.2.seat_number`.

Reserve all requested free preferred seats before assigning automatic seats, so an earlier automatic passenger cannot take a later passenger's chosen seat. Assign the remaining lowest free seats automatically. If there are fewer seats than passengers, confirm the available allocations and place the remaining passengers into FIFO order according to their order in the request. The review and receipt clearly distinguish confirmed seats from waiting positions. Cancelling any confirmed ticket promotes the first waiting passenger into that exact seat, regardless of which group they joined with.

Group booking uses one lock, one candidate state and one atomic persistence commit. It retains the existing storage schema and ordinary per-passenger records. Single booking remains compatible, and groups obey the same route/date/demo isolation rules. This feature does not introduce a group cancellation endpoint or a separate group lookup reference.
